# 2026-11-25 · Федотов · Загрузка резюме в MinIO и разбор в фоне

**Зона:** красная по данным (файл резюме с персональными данными попадает в хранилище)
и жёлтая (очередь и статус разбора). Правила хранения решал человек, ИИ их только реализовал.

**Задача.** Неделя 2 плана: загрузка резюме в MinIO и задача разбора в очереди.
Критерий из плана: «резюме → фоновая задача → список навыков».

**Что предложил ИИ:**
- порты `ResumeStorage` и `ParseQueue` и два набора адаптеров: MinIO и Celery для стенда,
  версии в памяти для тестов. Так логику можно проверить без контейнеров;
- клиент получает номер задачи и спрашивает статус, а не ждёт ответа — на неделе 3 разбор
  будет делать LLM, и это дольше (НФТ «карта за 30 секунд»);
- ошибку в файле (скан, повреждён) отдавать как статус с текстом, а сбой очереди — общим сообщением.

**Что решили сами и почему:**
- Пока нет входа, резюме загружает гость. Его файл **не храним**: удаляем сразу после разбора,
  даже если разбор упал. Это отдельный тест (152-ФЗ, риск Р-8).
- Без согласия на обработку данных файл не принимаем.
- Имя файла студента («Иванов_Иван_резюме.pdf») в ключ хранилища не попадает — ключ случайный.
- Профиль навыков студента и таблицы в базе делаем после слияния входа Моисеенко:
  без пользователей навыки не к кому привязать.

**Что проверил человек (без этого не сливаем):**
- [ ] Поднял `docker compose up`, загрузил своё резюме через `/api/docs`, получил навыки
- [ ] В консоли MinIO (порт 9001) после разбора файла в бакете нет
- [ ] Понимаю, зачем порты и почему тесты идут без MinIO и Celery
- [ ] `ruff check .`, `mypy`, `pytest` — зелёные локально или в CI

**Известные ограничения:** статусы задач хранятся в Redis сутки (настройка Celery по умолчанию).
Подсчёт токенов GigaChat на одно резюме — отдельная задача: нужен ключ API, его получаем через вуз.
